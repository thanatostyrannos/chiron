## Laguna: per-layer attention type, and the gating nobody documents

**Repository:** `architecture/transformers`

This is the reference model under study, and the file rewards reading before any Proteus design work. Two things to take from it. First, the SWA/global interleave is not an architectural abstraction -- it is a list lookup at layer construction time (`config.layer_types[layer_idx]`), which means the whole hybrid-ratio research question reduces to what goes in that list, and it is trivially ablatable. The shipped config gives 48 layers as 12 full + 36 sliding in a strict GSSS pattern with a 512-token window, i.e. the 3:1 ratio, verified from the artifact rather than quoted from a paper. Second, the MoE router is sigmoid with an aux-loss-free correction bias, which is the current answer to a contested question -- softmax routing makes experts compete for a fixed probability budget, sigmoid scores them independently, and the correction bias rebalances load by nudging selection while leaving the combination weights untouched. For a systems reader the router is a load balancer whose health signal is a learned bias rather than a queue depth; the analogy breaks because a mis-balanced expert does not just add latency, it permanently changes what that expert learns.

Every hybrid-ratio question this lab asks is a question about that list. |

> **Worth knowing:** Attention head count varies per layer. `LagunaAttention.__init__` takes `num_heads` as a constructor argument sourced from `config.num_attention_heads_per_layer`, rather than reading a single global `num_attention_heads` like essentially every open decoder implementation. The top-level config still advertises `num_attention_heads: 48`, so a reader who only looks at config.json will conclude the model is uniform when the code says otherwise -- and any KV-cost calculation done from the config alone is wrong for some layers.


## Laguna in llama.cpp: per-layer full/SWA selection and the two-tier KV cache

**Repository:** `architecture/llama-cpp-laguna`

Laguna's whole forward pass lives in one file, `src/models/laguna.cpp`: `load_arch_hparams` reads config into hparams, and a nested `graph` constructor emits the ggml node graph layer by layer. The full-vs-sliding-window decision is made once at load time — `set_swa_pattern(4, dense_first=true)` stamps a boolean per layer index (full at `il % 4 == 0`, SWA otherwise) — and everything downstream just reads that bit. The systems payoff is in `llama-kv-cache-iswa.cpp`: it allocates two entirely separate `llama_kv_cache` objects, a full-size one holding only the non-SWA layers and a small one sized to `n_swa + n_ubatch`, so 3 of every 4 layers pay window-sized residency instead of context-sized. That reads like a two-tier storage hierarchy, and the sizing math is exactly capacity planning — but the analogy breaks in three places worth internalizing: there is no promotion, demotion, or miss path between the tiers (a layer is bound to one tier forever by its index, decided from a GGUF key at load); "eviction" from the small tier is not a policy choice with a hit-rate cost, because `is_masked_swa` makes out-of-window tokens architecturally unreadable, so discarding them is lossless rather than a gamble; and the two tiers are not even numerically interchangeable, since full layers apply YaRN RoPE over 64 of 128 head dims at θ=500000 while SWA layers apply plain RoPE over all 128 at θ=10000. That last point means you cannot "just widen the windows" to test long context — the SWA layers were never trained with positional encoding that reaches past the window.

Second surprise: Laguna's full and SWA layers have different `n_head` (48 vs 64 in XS.2), so the two layer types are structurally different tensors, not the same block with a different mask.


## PagedAttention: the block table

**Repository:** `memory/vllm`

vLLM's block table is the structure a kernel engineer already owns, split across two processes. Scheduler-side, `req_to_blocks` is a per-sequence page table -- a plain list whose index is the logical KV block and whose `KVCacheBlock.block_id` is the physical frame into one giant preallocated KV tensor; worker-side it is flattened into a dense `[max_num_reqs, max_num_blocks_per_req]` int32 matrix copied to the GPU each step, and the attention kernel walks it itself, one load per KV tile per head per layer, with no MMU and no TLB caching the translation. The analogy breaks in three places worth internalizing. First, there is no page fault: nothing is demand-paged, so `allocate_slots` returning None is not a fault to be serviced but an admission rejection that preempts the entire request -- eviction granularity is the sequence, not the page. Second, the free list is not a free list; `FreeKVCacheBlockQueue` holds ref_cnt==0 blocks with their contents and hashes intact so `touch()` can resurrect one on a prefix hit, which makes the free list and the LRU victim cache the same linked list, and is why `free_blocks` is called with a request's blocks reversed so tail blocks sit nearest the front of the eviction order. Third, the page size is denominated in tokens rather than bytes -- `page_size_bytes` in `kv_cache_interface.py` differs per layer type -- so a hybrid SWA/full-attention model runs several independent block tables with different frame geometry over the same physical pool, something no single-address-space page table has to model.

> **Worth knowing:** The prefix cache deliberately refuses to de-duplicate identical blocks. The `BlockHashToBlockMap` docstring (block_pool.py:47-51) states that when a block becomes full and is cached, vLLM does not check whether an identical block already exists -- two sequences that independently produce the same KV content keep two physical copies forever. The stated reason is that collapsing them would change an already-issued block_id, and block table rows must remain strictly append-only. So sharing happens only at lookup time, before allocation, never retroactively: the opposite of what page-dedup (KSM) or the paper's copy-on-write framing leads you to expect, and it means the append-only invariant on the block table is being paid for in wasted physical memory.


## Prefix cache: the block-hash chain, the hit path, and refcounted eviction

**Repository:** `memory/vllm`

Read this as a page table plus a refcounted buffer cache. Each request owns a block table mapping logical token-block index to a physical KV block id, exactly like a VA->PA mapping, and `get_cached_block` is a dedup probe against a global hash table (`cached_block_hash_to_block`) that lets two requests point at the same physical page — closer to KSM/CoW page sharing than to a per-process cache. The free list (`FreeKVCacheBlockQueue` in kv_cache_utils.py) is a hand-rolled intrusive doubly-linked list precisely so `touch` can splice a block out of the LRU in O(1) on a hit, and `free_blocks` (block_pool.py) is a two-tier reclaim: hash-less blocks get prepended (die first), hashed blocks appended to the tail so they linger as reuse candidates. Where the analogy breaks: the lookup key is a *chain* — `hash_block_tokens` folds the parent hash in — so it is position-dependent and strictly prefix-ordered. The same 16 tokens at a different offset are a different key, one changed token at position 0 invalidates every downstream hash, and there is no associative or middle-of-sequence match; the loop breaks at the first miss because a later hit is impossible by construction. Second break: a hit removes *compute*, not I/O, and the working set is not the model's — it is the union of live conversation prefixes, which means hit rate is governed by request routing and system-prompt sharing far more than by cache size.

|---|---|

> **Worth knowing:** Two things contradict the usual "prefix caching skips the repeated tokens" story. First, a 100% prefix match never skips 100% of the work: `get_computed_blocks` caps the hit at `request.num_tokens - 1` because you need a forward pass to get logits, and since the result is then floored to block alignment, an exact-duplicate prompt recomputes an entire trailing block (16 tokens by default), not one token. Second, freeing is not evicting — `free_blocks` only decrements ref_cnt and pushes the block back on the LRU while leaving its entry live in `cached_block_hash_to_block`, so a zero-refcount block is still matchable and a later request can resurrect it. Eviction happens lazily inside `get_new_blocks` -> `_maybe_evict_cached_block` at the moment of reallocation, which is why "cache blocks in use" and "cache entries available for hits" are two different, non-obvious numbers.


## RadixAttention: the prefix tree, its lookup, and its eviction

**Repository:** `memory/sglang`

Three levels of indirection, and the bottom two will feel familiar. `ReqToTokenPool.req_to_token` is a dense int32 `[req_slot, position] -> kv_slot` table — a per-process page table with position as the VPN and the KV slot as the PFN — sitting on a paged frame allocator whose `free()` coalesces to page granularity via `torch.unique(free_index // page_size)`. The radix tree on top is not a TLB-style cache but a content-addressed dedup layer over extents: each `TreeNode` owns a *run* of KV slots, and `_split_node` cleaves that run when a new sequence diverges mid-node — the same move as splitting a filesystem extent on a partial overwrite. Two places the analogy breaks. First, there is no fault path: a page-table miss traps and pages in, whereas a radix miss just means recompute, and eviction is destructive — the only "reload" is a full prefill (`hiradix_cache.py` bolts on a host tier; plain `RadixCache` has none, so this is a cache with no backing store). Second, eviction is topologically constrained rather than recency-ordered: `evict()` only ever considers *leaves* drawn from an incrementally maintained `evictable_leaves` set (`_update_leaf_status`, line 790), peeling the frontier inward, so a hot child keeps a cold parent resident indefinitely — and `inc_lock_ref` walks all the way to the root, letting one in-flight request pin an arbitrarily deep prefix chain, closer to a pinned dentry chain than to a page refcount.

## FlashInfer paged KV cache: the plan API and NHD vs HND layout

**Repository:** `memory/flashinfer`

The three tensors `kv_indptr`, `kv_indices`, `kv_last_page_len` are a CSR-encoded per-process page table: `indptr` is the per-request offset array into a flat list of physical page IDs, and `last_page_len` is the valid-entry count in the partially filled tail page — exactly the block-allocated-file arrangement where the inode holds block numbers and the last block is short. Fixed-size pages buy the same thing they buy a kernel allocator: O(1) allocation, no external fragmentation, and internal waste bounded at under one page per request, which `get_seq_lens` in page.py makes arithmetic. The analogy breaks in three specific places. First, there is no fault handler and no present bit: a page is in the table or it does not exist, so eviction is destruction rather than demotion to a slower tier, and a "miss" is simply unrepresentable inside the kernel. Second, translation is not per-access and not done by hardware — `plan()` copies the indptr to the host (decode.py:1481), walks it once to compute a split-k work partition, and that partition is then reused verbatim across every transformer layer, so this is a query planner, not an MMU; the page table is frozen for the duration of a forward pass. Third, `last_page_len` is bounded `1 <= n <= page_size` (decode.py:736), not `0 <= n < page_size`, so a full page reads as 16 and an empty request cannot be encoded at all. NHD vs HND is the stride order *inside* a page — whether tokens or heads are the outer axis — and it determines whether a kernel loading one head's slice of a page performs a contiguous burst or a strided gather.

## Mooncake Store: KV cache as a storage hierarchy (transfer engine, put/get, eviction & placement)

**Repository:** `memory/mooncake`

Read Mooncake as two separate machines glued by a lease. The TransferEngine is pure DMA plumbing — pin a buffer, get a handle to a remote peer's registered region, post a batch of (READ|WRITE, local pointer, segment id, offset, length); it is `pread`/`pwrite` against someone else's address space with the target CPU uninvolved, and it knows nothing about keys. Everything that looks like a page table — key to (segment, offset, replica type) — lives in a separate metadata master, so a Put is a two-phase commit (PutStart hands you addresses, you RDMA the bytes yourself, PutEnd publishes) and a Get is "ask the master for descriptors, pick a tier with SelectBestReplica, then DMA." The tiering is genuinely a storage hierarchy — DRAM segments over RDMA, local NVMe, shared NVMe, CXL — with watermark-triggered writeback (BatchOffload), free-ratio placement, and frequency-gated promotion back up. Where it breaks from the systems intuition: the working set is defined by *leases*, not recency. An object is not evictable until its lease expires; `Get` renews the lease, and `BatchEvict` then ranks the already-expired set by lease deadline. So this is closer to leased/reference-counted pages in a distributed filesystem than to an LRU chain, and the "hot" signal is a TTL renewal rather than a touch bit. The deeper break is correctness: evicting a KV block is never data loss, only a recompute, which is why `offload_force_evict` can throw bytes away rather than block on writeback — a tradeoff no real storage tier is allowed to make.

## Mamba-2 SSD: the chunked scan and the fixed-size carry

**Repository:** `architecture/mamba`

Attention's KV cache is a working set that grows linearly with context: an append-only log you must eventually evict from, indexed per token. Mamba-2 replaces it with a fixed-size register file — `ssm_state` is allocated with shape `(batch, nheads, headdim, d_state)` and no `seqlen` term at all, so per-layer decode footprint is byte-identical at 1K and 1M tokens (defaults `d_state=128`, `headdim=64`, `chunk_size=256`). The chunked scan is the systems trick that makes training this thing fast: split the sequence into fixed 256-token chunks, compute each chunk's local contribution independently with dense matmuls, then run a cheap sequential recurrence over only the `L/256` chunk *boundaries* to thread the carry — structurally the same two-phase shape as a segmented prefix-sum, or as replaying a checkpointed WAL where per-segment deltas are computed in parallel and folded in strict order afterward. The `initial_states` / `return_final_states` parameters on the kernel entry point are the cross-request prefix-reuse hook: snapshot the state after a shared prefix, hand it to the next call — the SSM analogue of prefix KV reuse, except it is one small tensor instead of a block table. **Where the analogy breaks:** this is not a cache, because there is no addressable slot per token — the carry is overwritten in place by a decay multiply (`states = scale * states + new_states`), so nothing can be evicted, selectively recomputed, or attributed back to a specific past token, and you cannot page it in from a lower tier because the information was destroyed, not relocated. The second break: "constant state" is a *decode-time* property only — during training and prefill the forward pass materializes one fp32 state per chunk before the boundary pass runs, so activation memory there is O(L/chunk_size), not O(1).

## Gated DeltaNet: the state update rule (decay tick + delta write)

**Repository:** `architecture/flash-linear-attention`

The entire "memory" of a Gated DeltaNet head is one K×V float matrix `h` — fixed size, independent of sequence length — and every token performs the same three-step read-modify-write against it: scale the whole matrix by a scalar decay `exp(g)`, read back what the matrix currently returns for this token's key (`h^T k`), then add a rank-1 outer product of that key with `beta * (v - h^T k)`. That middle step is the delta (error-correction) term and it is what separates this from plain accumulation: the layer writes the *residual* between the value it wants stored and the value already retrievable, so `beta=1` is an exact overwrite of that key's slot, `beta=0` is a no-op, and values in between are a partial overwrite. Note the ordering — decay is applied *before* the residual is computed, so the correction is measured against the post-decay state, not the pre-decay one. Bridging to systems: it behaves like a fully-associative cache with a global TTL tick, where `beta` is write strength and the delta term is a compare-and-swap against whatever is currently resident. The analogy breaks in three specific places. (1) There are no lines or addresses — keys are L2-normalized continuous vectors, so every write smears across the whole matrix and a *similar* key partially clobbers a neighbour's content; the failure mode is interference, not a miss. (2) There is no capacity miss, no eviction policy, and no backing tier to spill to: the decay multiply destroys old content every single step whether or not new content arrives, and there is nowhere to re-fetch it from. (3) It is emphatically not a WAL — a transformer KV cache is an append-only exact log you can re-scan, whereas this state is destructive-update and unreplayable, so token 5's exact contribution cannot be recovered at token 5000. Capacity is O(1) in T instead of O(T); what you pay is that recall is lossy and degrades by interference rather than by explicit eviction.

> **Worth knowing:** The "gated" half of Gated DeltaNet cannot forget selectively. So the mental model of "gating = selective forgetting" is backwards here: the gate is an indiscriminate global decay, and the delta is the targeted erase.


## Samba: choosing the layer type by modulo on layer index

**Repository:** `architecture/samba`

Samba does not store a layer schedule; it recomputes one from `layer_idx % mb_per_layer` inside each block's constructor, the way a striping function derives a device from a block number rather than consulting a map. With `mb_per_layer = 2` the implemented ratio is 1:1 Mamba to attention, with an MLP after every one of them, so the repeating period is four sublayers (Mamba, MLP, sliding-window attention, MLP) and a 12-layer model gets exactly 6 Mamba and 6 attention layers. The systems payoff is in the KV cache: only half the layers hold one, and because `full_per_layer` defaults to a million every one of those is clamped to a 2048-token window, so total KV footprint is fixed rather than growing with sequence length -- a per-layer ring buffer instead of an append-only log. The useful mental model is a two-tier store where the attention window is a bounded buffer of recent raw records and the Mamba state is a lossy rolling summary of everything older. **Where the analogy breaks:** there is no miss path and no promotion. Nothing evicted from the 2048-token window is ever faulted back in, there is no backing store to fault from, and the model cannot detect that a miss occurred; furthermore both "tiers" execute on every token in sequence rather than one being consulted only when the other misses, so you always pay for both.

## Checkpoint sharding and mid-epoch dataloader resume

**Repository:** `training/olmo-core`

A checkpoint here is an object store, not a memory image: the `.metadata` file maps each logical tensor slice to a `(relative_path, offset, length)` extent inside one of N `.distcp` files, and on load each rank issues byte-range reads for only the extents its own shard covers — structurally a page table plus range GETs, except the extents are variable-length, greedily bin-packed by writer thread, and re-laid-out on every save, so nothing is stable across checkpoints except the logical key. Optimizer state rides along keyed by parameter FQN rather than by rank or by the integer param index vanilla PyTorch uses, which is exactly why a run saved under one FSDP topology loads under another: resharding is re-indexing, not data movement, and `full_state_dict=False, cpu_offload=True` means nothing is ever gathered to rank 0. The analogy breaks on the write side — there is no journal and no incremental delta; every save is a full rewrite, committed by writing into a `<dir>-tmp` sibling and doing a directory rename, so atomicity is rename-granularity, not record-granularity, and a torn save loses the whole checkpoint rather than a tail. The dataloader is not a WAL either: it stores a cursor, not a log. It reconstructs the epoch's entire global instance order as a pure function of (seed, epoch, dataset length, chunk size) into a uint32 memmap in the work dir, then slices off the first `batches_processed` rows and re-derives the per-DP-rank and per-worker stride from the same arithmetic — so there is zero per-worker iterator state to persist, and the price of a restart is recomputing a permutation rather than replaying work.

## OLMo-core: the training step, gradient accumulation, and telemetry emission

**Repository:** `training/olmo-core`

The loop is split across two objects with a clean control/data-plane boundary: `Trainer` owns scheduling, bookkeeping, and callbacks but never touches a tensor, while a `TrainModule` owns the model, optimizer, and everything device-side. `Trainer._fit_epoch` is the scheduler thread — it advances `global_step`, fires callback hooks, then calls `train_batch` / `optim_step` / `zero_grads` on the module, in that order. Gradient accumulation is not a counter as in most codebases; it is a spatial split — `split_batch` chops the rank's batch into micro-batches sized by `rank_microbatch_size`, and each micro-batch does its own forward and its own `loss.backward()`, so gradients accumulate in the `.grad` buffers exactly the way a read-modify-write accumulator does. The systems analogy that holds: `_train_microbatch_context` is write-combining. Collective gradient reduction is the expensive bus transaction, so DDP `no_sync()` / FSDP `set_is_last_backward` suppress it on every micro-batch but the last, coalescing N reductions into one — same idea as deferring a cache-line writeback until the line is evicted. Where the analogy breaks: unlike a writeback cache there is no correctness fallback if you get the flush point wrong. Skipping the final sync does not cost you latency, it silently trains each rank on its own local gradient and the run diverges with no error, which is why the flush point is a context manager rather than a flag. The second breakage is on telemetry: `record_metric` writes into a plain in-process dict keyed by step, and `_log_metrics` only drains it every `metrics_collect_interval` steps (default 5). This looks like a WAL with group commit, but it has none of a WAL's durability — the buffer is volatile, and the reason for batching is not I/O amortization but avoiding a host-device sync. Reading a CUDA tensor's value stalls the GPU pipeline, so metrics are kept as unevaluated device tensors, moved to the bookkeeping device in one shot, and then reduced across ranks on a background thread over a separate CPU process group. Observability here costs training throughput directly, which is not true of any logging system you have run in production.

> **Worth knowing:** The loss is divided by the whole-batch token count *before* backward (`loss_div_factor=batch_num_tokens_for_loss`, and in the basic module `ce_loss.div_(batch_num_tokens_for_loss)`), so gradients are never rescaled by the number of micro-batches afterward — the usual "divide by accumulation steps" step simply does not exist. This is not cosmetic: it makes the gradient correct even when micro-batches are ragged or unequal in size, which the standard mean-of-means formulation gets subtly wrong. The other surprise is that the reference `TransformerTrainModule` deliberately re-implements `train_batch` rather than reusing `BasicTrainModule`'s version — the two are near-duplicates, and `BasicTrainModule` is effectively a teaching artifact, not the code that trains OLMo.


## nanoGPT: the known-good run for the Hardware Validation Gate

**Repository:** `training/nanogpt`

Read `get_batch` as a mmap-backed table scan with no cursor: the dataset is one flat uint16 array, the OS page cache is the entire data tier, and the shakespeare_char working set (~1MB train.bin) is resident after the first pass, so I/O disappears and the step time you measure is pure compute plus host-to-device copy. `block_size = 256` looks like a cache size but behaves like a fixed address space — `wpe` is a learned lookup table with exactly block_size rows (model.py:128), so there is no fault-in path for position 257; the code either does surgery to shrink it (`crop_block_size`) or truncates the left of the sequence at sample time (model.py:314). That is the first place the caching analogy breaks: no miss handling exists, only eviction-by-truncation, and the eviction policy is hardcoded as "drop the oldest." The second break is that the thing our lab studies is absent here — training keeps zero state between steps, K and V are recomputed from the residual stream on every forward (model.py:56) and discarded, so nanoGPT has no KV cache to instrument; `generate` (model.py:306) re-runs the full prefix per sampled token, quadratic and cacheless by design. Finally, do not read the loss like a latency SLO: 1.4697 is per-character cross-entropy in nats (~2.12 bits/char), an information-theoretic quantity, and `estimate_loss` samples 200 random batches, so reproducing it to four decimals on gfx1151 is not the bar — landing inside roughly a hundredth of it is.

> **Worth knowing:** Two things bite the validation gate specifically. First, the MFU percentage `train.py` prints every log_interval (train.py:327) is computed against a hardcoded `flops_promised = 312e12` — A100 bf16 peak — at model.py:301, so on the 8060S it is a meaningless ratio and will read absurdly low even when hipBLASLt is configured correctly; the denominator must be changed before that number can serve as the "GEMM throughput sane, not 5x low" signal. Second, despite `torch.manual_seed(1337)` at train.py:106, resuming restores only model, optimizer, iter_num and best_val_loss (train.py:158-180) — never the RNG state and never a data position, because `get_batch` samples offsets with replacement from global RNG. A resumed run therefore diverges from an uninterrupted one by construction, so the gate's checkpoint round-trip check has to compare saved-vs-loaded weights bit-exactly rather than compare loss trajectories across a restart.
